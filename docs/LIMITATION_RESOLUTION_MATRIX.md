# Limitation Resolution Matrix

Each row follows: Limitation → Original Risk → Proposed Solution → Implemented? (planning stage — set at build time) → MVP Result → Remaining Gap. This matrix should be updated with actual results once each item is built (Milestone 10, documentation pass).

| Limitation | Original Risk | Proposed Solution | Implemented? | MVP Result (fill in during build) | Remaining Gap |
|---|---|---|---|---|---|
| No physical sensors | No live telemetry to analyze | Hardware-agnostic ingestion interface + deterministic telemetry simulator + CSV upload, all writing to one `measurements` schema | **Yes** | Simulator and CSV both normalize into the same `NormalizedMeasurement` shape and the same service layer (`app/services/telemetry_service.py`); the Intelligence Core (Milestone 3+) will consume this without knowing the source | Real IoT/BMS integration itself is not built — only the interface it will plug into (`FUTURE_SCOPE.md`) |
| Limited historical data | Weak/unreliable baseline | Deterministic historical-data generator producing 10 weeks of realistic daily/weekly patterns, occupancy, operating hours, noise, trend; explicit cold-start gating (`insufficient_history`) rather than fabricated confidence | Partial | 10-week generator implemented and statistically verified (weekday/weekend and operating/closed-hours differences confirmed, see `TESTING.md`); the cold-start gate itself is a Baseline Engine responsibility, built in Milestone 3 | Real deployments still need real elapsed time to accumulate trustworthy history |
| False positives / alert fatigue | Too many low-value alerts | Multi-signal anomaly engine (deviation + persistence + operating status + occupancy + cross-resource correlation) with 4 severity levels and an `unusual` vs `operationally_suspicious` distinction | **Yes** | Implemented and tuned against real output: a `limited`-confidence (cold-start fallback) baseline was found to flood early weeks with spurious flags during development and was fixed to never flag on its own (`ANOMALY_DETECTION.md`); the legitimate-spike scenario is verified to never reach `operationally_suspicious` | Threshold/weight tuning is still heuristic, not learned from a large real dataset — documented as a future ML upgrade path |
| AI hallucination | Incorrect or invented reasoning shown as fact | Structured input (evidence packet only) + structured output schema + grounding validation (causes/evidence must reference the given packet) + no-new-numbers check + deterministic fallback engine | **Yes** | Implemented (`app/ai/grounding.py`) and tested against invented causes, invented evidence references, and invented numbers in free text — each is independently caught and triggers fallback (13 dedicated tests in `tests/ai/test_grounding.py` and `tests/ai/test_investigation_service.py`) | The numeric-grounding check is a heuristic (regex-extracted numbers matched against evidence values within a small tolerance), not a formal proof of non-hallucination — it catches invented/altered numbers reliably but cannot catch every conceivable subtle misstatement in free-text reasoning |
| Emission-factor uncertainty | Incorrect/opaque CO2e figures | Configurable, versioned emission-factor registry with source citation | **Yes** | Implemented (`app/services/factor_service.py`, `app/models/factors.py`); `GET`/`PUT /api/config/factors/...` let the registry be read and updated without a code change | Snapshotting the factor value onto each `impact_records` row (so historical figures survive a later factor update) is deferred to Milestone 5 when `impact_records` are actually written; default seed factors are explicitly labeled illustrative pending a finalized citation |
| Difficulty verifying savings | Can't prove an intervention worked | Full deterministic pre/post-intervention comparison workflow (reusing the Milestone 3 baseline engine, no second methodology) with explicit `insufficient_data`/`no_measurable_improvement`/`improvement_detected`/`verified` states and a minimum-data gate | **Yes** | Implemented (`app/services/verification_service.py`); tested against genuine improvement, no improvement (a dishonestly early completion correctly produces `no_measurable_improvement`), insufficient data, and a context-mismatch downgrade — 165 tests passing including `tests/services/test_numerical_integrity.py`'s adversarial checks | The verification window is bounded by the demo's pre-generated dataset (a few days of "recovery" telemetry after the leak); a real deployment needs real elapsed time to accumulate a comparable post-intervention window |
| Artificial-looking demo data | Weak credibility with judges | Proper deterministic telemetry simulator with realistic seasonality/noise/occupancy/operating-hours modeling, not manually fabricated rows; 6 named reproducible scenarios | **Yes** | Implemented and statistically inspected (not just row counts) — e.g. weekday midday electricity ~43 kWh vs weekend ~4 kWh; water leak window ~14 L/hr vs an ordinary closed-hours baseline of ~1 L/hr, sustained and flat rather than a spike; post-intervention window returns to ~1 L/hr | Simulated data, however realistic, is still not real-world sensor data — explicitly disclosed, not hidden |
| Lack of real-world validation | Unproven system | Scenario validation framework: normal / water leak / electricity overconsumption / closed-building-continued-use / legitimate spike / post-intervention recovery, each with asserted expected outcomes | **Yes** | All 6 scenarios implemented with automated tests asserting the specific expected pattern for each (not just "a value changed") — see `TESTING.md` | No real building deployment yet — validation is against realistic synthetic scenarios, not field data; anomaly *detection* against these scenarios is Milestone 3 |
| Limited scalability | Schema/architecture too narrow | Generic Resource/Measurement architecture shared by electricity and water, extensible to more resource types without schema changes beyond a new enum value | **Yes** | Implemented as designed — `Resource`/`Measurement` tables are shared, not duplicated, across electricity and water | Multi-tenant, multi-organization scaling is explicitly out of MVP scope (`FUTURE_SCOPE.md`) |
| AI provider failure | App breaks if AI API is down | Deterministic fallback investigation engine producing an equivalent structured output from the same evidence, with `explanation_source` transparently labeled | **Yes** | Implemented (`app/ai/fallback.py`) and verified against the real Greenfield Public School dataset with no API key configured — the full detect → investigate loop works end-to-end via `python -m app.cli investigate-demo` (see `DEMO.md`); also tested against timeouts, malformed responses, and generic API errors, all correctly triggering fallback | Fallback explanations are template-based and less flexible in phrasing than the AI path — an intentional trade-off for reliability |

*"Implemented?" and "MVP Result" columns are marked "Planned" at this planning stage per the instruction not to write application code yet; this matrix should be revisited and filled in with actual outcomes as each milestone in `ROADMAP.md` completes.*
